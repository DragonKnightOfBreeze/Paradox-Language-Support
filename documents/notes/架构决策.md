#### 重构作用域和作用域方法 - 改为偏好使用成员方法作为作用域方法，而非带上下文参数的扩展方法

> - 版本：v2.1.8
> - 日期：2026-05-08
> - 状态：已实施

说明：
- 这里的作用域指的是某种接口或类，对应某种限定的API范围，某些情况下还带有自己的上下文。`SequenceScope` 和 `CoroutineScope` 都是典型的作用域。
- 区别于普通的工具方法和扩展方法，作用域方法只能在对应的作用域中使用。例如，将作用域对象作为 `this`，或者上下文参数 `context(scope: Scope)`。
- 改为偏好使用成员方法作为作用域方法，而非带上下文参数的扩展方法。除非不存在一个明确的可控制的作用域（类/接口）。

目的：
- 即使上下文中不存在符合条件的作用域对象，IDE 仍会补全作为扩展方法的那些作用域方法。
- 改为使用成员方法的话，可以避免这种非理想的行为，并且允许隐藏实现细节。

相关代码位置：
- `icu.windea.pls.config.select.CwtConfigSelectScope`
- `icu.windea.pls.lang.select.ParadoxSelectScope`

#### 重构 path/expression/complexExpression/config/configExpression - 更改解析器与解析方法的代码风格

> - 版本：v2.1.10
> - 日期：2026-06-14
> - 状态：已实施

说明：
- 将对外的解析方法改为模型接口上的静态方法，委托给解析器类（可能是单例对象，可能是私有的）的对应方法。
- 解析器类通常是同文件中的私有类，少数情况下也可以是不同文件中的公开类。
- 偏好上，将同文件中的私有实现方法放到公开接口方法之后，并且使用 `region...endregion` 注释包围。
- 偏好上，将文档注释放到接口代码上，实现代码（以及公开的解析器类的代码）通常不需要文档注释。

目的：
- 为了统一代码风格。

示例（不需要公开解析类的情况）：

```kotlin
interface Expression {
    val value: String
    
    companion object {
        @JvmStatic
        fun resolve(text: String): Expression = ExpressionResolver.resolve(text)
    }
}

// region Implementations

private object ExpressionResolver {
    fun resolve(text: String): Expression {
        return ExpressionImpl(text)
    }
}

private data class ExpressionImpl(override val value: String)

// endregion
```

#### 关于上下文对象（context object） {#context-object}

> - 版本：v2.1.10
> - 日期：2026-06-20
> - 状态：记录中

说明：
- 上下文对象应当被声明为数据类，其属性应尽可能不可变，可以有计算属性和一些工具方法。
- 上下文对象的切换是通过复制当前上下文，并按需更改特定的属性来达成的。
- 切换上下文时，不一定需要直接传递复制后的上下文对象，或是声明并传递不同名的局部变量。
- 一般来说，上下文的切换可以随编程语言（Kotlin）的作用域的切换而按需切换，直接声明同名的局部变量并覆盖（如在循环中）。

#### 集合选型（collection selection） {#collection-selection}

> - 版本：v3.0.1
> - 日期：2026-07-20
> - 状态：记录中

主要考量是在特定场景下的内存占用的细节，其次是作为一种统一的规范。

- `ArrayList` - 不需要保证线程安全的可变列表的默认选择。通常是但并不总是符合前述条件时的最佳选择。
- `SmartList` - 当长度为1时，相比 `ArrayList` 有着更少的内存占用。如果存在大量长度为1的不需要保证线程安全的不可变列表，这会是更好的选择。
- `ImmutableList` (guava) - 不可变列表，拥有更少的内存占用。对于反序列化后的索引数据、不可变缓存、以及部分轻量的无需缓存的计算结果，这会是更好（且优先）的选择。
- `IntArrayList` 等 (fastutil) - 不适合直接使用数组，且元素是原始类型时，这会是更好（且优先）的选择。
- `ObjectArrayList` (fastutil) - 相比 `ArrayList` 并没有明显的性能优势，仅在绝对必要时使用。例如需要使用到独有的API（如 `trim()`）。或者，作为一种统一的规范。
- `HashSet` - 不需要保证线程安全且不需要保证元素顺序的可变集的默认选择。通常是但同样并不总是符合前述条件时的最佳选择。
- `LinkedHashSet` - 在前者的基础上，如果需要保证元素顺序。
- `ImmutableList` (guava) - 不可变集，拥有更少的内存占用。对于反序列化后的索引数据、不可变缓存、以及部分轻量的无需缓存的计算结果，这会是更好（且优先）的选择。
- `IntOpenHashSet` 等 (fastutil) - 元素是原始类型时，这会是更好（且优先）的选择。
- `ObjectOpenHashSet` (fastutil) - 拥有相对较少的内存占用。如果存在大量集，可以考虑使用。
  - 参见：`com.intellij.util.containers.CollectionFactory.createSmallMemoryFootprintSet()`
- `ObjectOpenLinkedHashSet` (fastutil) - 在前者的基础上，如果需要保证元素顺序。
  - 参见：`com.intellij.util.containers.CollectionFactory.createSmallMemoryFootprintLinkedSet()`
- `ObjectLinkedOpenCustomHashSet` (fastutil) - 可以用来创建大小写不敏感的字符串集。
  - 参见：`com.intellij.util.containers.CollectionFactory.createCaseInsensitiveStringSet()`
- `ObjectArraySet` (fastutil) - 拥有更少的内存占用。如果存在大量集，并且重排序时的性能相比之下并不重要，这会是更好的选择。
- `ImmutableMap` (guava) - 不可变映射，拥有更少的内存占用。对于反序列化后的索引数据、不可变缓存、以及部分轻量的无需缓存的计算结果，这会是更好（且优先）的选择。
- `Int2ObjectOpenHashMap` 等 (fastutil) - 元素是原始类型时，这会是更好（且优先）的选择。
- `Object2ObjectOpenHashMap` (fastutil) - 拥有相对较少的内存占用。如果存在大量映射，可以考虑使用。
  - 参见：`com.intellij.util.containers.CollectionFactory.createSmallMemoryFootprintMap()`
- `Object2ObjectLinkedOpenHashMap` (fastutil) - 在前者的基础上，如果需要保证元素顺序。
  - 参见：`com.intellij.util.containers.CollectionFactory.createSmallMemoryFootprintLinkedMap()`
- `Object2ObjectOpenCustomHashMap` (fastutil) - 可以用来创建键为忽略大小写的字符串的映射。
  - 参见：`com.intellij.util.containers.CollectionFactory.createCaseInsensitiveStringMap()`
- `Object2ObjectArrayMap` (fastutil) - 拥有更少的内存占用。如果存在大量映射，并且重排序时的性能相比之下并不重要，这会是更好的选择。

#### 懒加载的魔法与24字节的摩擦  {#lazy-value-magic}

> - 版本：v3.0.2
> - 日期：2026-08-10
> - 状态：记录中

说明：
- Kotlin 标准库中提供的 `lazy {...}` 会带来额外的24字节的内存开销（对象本身+3个字段）。
- 在大多数情况下，通过使用内存友好的懒加载属性（基于 `@Volatile`，或者基于 `@Volatile` 和双重检查锁），可以避免这些内存开销。
- `LazyValue` 的伴生对象上提供了一组内联构建方法，用于以统一且相对简洁的格式，实现内存友好的懒加载属性。

#### 引号模式与引号处理 {#quote-pattern}

> - 版本：v3.0.2
> - 日期：2026-08-23
> - 状态：已实施

说明：
- 进一步的对引号处理的相关重构：引入 `QuotePattern`。
- 这是一种“策略模型”类，既包含相关的元数据，也作为对断言和修改逻辑的策略。
- 相关的接口代码与实现代码统一移到 `icu.windea.pls.core.text`。
- 在 `icu.windea.pls.core.TextExtensions.kt` 中提供相关的扩展方法。

作为一个例子，脚本文件（以及CWT规则文件和CSV文件）中的字符串字面量（比如 `k = v` 中的 k 和 v）是可以用双引号括起的，两种格式基本上是等效的。
这就引出了一些微妙的问题。比如在各种地方要用到的那个字符串，可能需要去除双引号，可能需要保留，可能需要仅在必要时保留。
比如插件提供了意向以去除/加上字面量周围的双引号，但是如果包含一些特定字符（不同文件类型之间存在区别），就不能去除，否则会破坏语法。

通用的工具方法，例如 `String.quoteIfNeeded`，应改为可以传入 `quotePattern` 作为参数，并且默认使用 `QuotePattern.Default`。
对于脚本文件内容，因而可以改为直接使用 `String.quoteIfNeeded(QuotePattern.ParadoxScript)`，这是一种更加直观和简洁的写法。

相比 `QuotePattern`，另一种可能的命名方式是 `QuotePolicy` 或 `QuoteStrategy`。
然而，考虑到与已有的 `TextPattern` 的对齐，以及这确实会携带一些只读数据，仍然选择使用 `QuotePattern`。

对于除了 `needQuote` `canQuote` `canUnquote` `quoteIfNeeded` 以外的所有断言和修改方法，实现细节预期是等效的。
因此调用对应的扩展函数时，可以不显式指定参数 `quotePattern`。

相关代码位置：
- [x] `icu.windea.pls.core.text.EscapePattern`

#### 完善脚本文件的 lexer {#script-lexer-refactor}

> - 版本：v3.0.2
> - 日期：2026-08-27
> - 状态：已实施（告一段落）

说明：
- 需要在内部维护堆栈（`stateStack`），以记录上下文状态（退出时需要回退到的状态）。例如，在 `key_$PARAM$ = value` 中，从 `IN_PARAMETER` 回退到 `IN_KEY`。
- 需要在内部维护堆栈（`expectStack`），以记录当前期望的构造类型（回退上下文状态时，类型需要匹配）。例如，如果遇到 `{`，则期望的构造类型应设置为 `EXPECT_BLOCK`。
- 需要在处理时，按需允许和跳过空白词元（`TokenType.WHITE_SPACE`）。
- 通过 `enterState(state, expect)` 和 `exitState(expect)` 进行入栈和出栈。
- 如果下游状态中遇到了无法直接匹配的字符（例如，某个上游状态的边界，如 `}`），应逐步回退到上游状态（通过 `[^] { exitState(); yypushback(yylength()); }`），交由那个上游状态处理，从而简化代码。

目的：
- 为了达成更准确的词法分析：更好的对可选空白和高级插值语法（如 `a_$p$_[[p]b]`）的支持，更完善的错误恢复策略。
- 为了便于后续重构：仍然存在更多的细节和边界情况，需要进一步的研究、设计和调整。

- 如果返回 `null` 则表示不存在，并且不一定期望存在。如果返回空列表则表示不存在，并且期望存在（已经预先执行了一定的匹配逻辑，导致打平后被完全过滤，应被报告为无法解析的表达式）。
- 需要兼容成员树（不仅是当前成员）中带参数的情况。
- 需要兼容成员树中匹配到了 `$any` 数据类型的情况。
- 进行代码检查时，遍历一个节点时可能不保证会先遍历其父节点，因此可能无法通过本地堆栈的方式判断某个表达式是否真的无法被解析（上层成员可能带参数）。需要验证。

思路2：在 `configContextProvider` 中新增方法，以决定是否跳过 `UnresolvedExpressionInspection`
- 如果 `configContext.inRoot()` 为 `false`，则需要跳过。这意味着当前位于某种根上下文之外，例如位于定义声明之外。我们目前不检查这种情况，但未来需要考虑进一步完善（并且，需要使用不同的报错信息）。

#### 完善作用域的匹配和合并逻辑，兼容并集作用域 {#union-scopes}

> - 版本：v3.0.2
> - 日期：2026-08-25
> - 状态：已实施

说明：
- 主要目的是为了兼容 Stellaris 中的 `carrier` 作用域。
- 或者称之为“带继承关系的作用域”。
- 考虑复用并应用作用域规则的字段 `is_subscope_of`。

备注：
- `scopeConfig.is_subscope_of` 应在使用时保证是正确的（这意味着不再检查是否存在意外的递归），如果不正确，应在解析规则时就打印警告日志。
- 基于父作用域的匹配和合并需要递归进行。
- 父作用域不会匹配子作用域。

作用域的匹配逻辑（scope -> scopeToMatch）：
- scope 是输入的数据（从上下文中获取或推断）。
- scopeToMatch 应来自可信的数据源（规则文件或代码实现）。
- 如果 scope 为 `null`，则直接匹配。
- 如果 scopeToMatch 为 `any`，则直接匹配（scopeToMatch 不应为 `?`，不处理这种情况）。
- 如果 scope 为 `any` 或 `?`，则直接匹配。
- 如果 scope 的 ID 完全匹配 scopeToMatch，则匹配（比较字符串，值相等，不忽略大小写）。
- 如果 scope 存在别名（来自 `scopeConfig.aliases`），则尝试用这些别名完全匹配 scopeToMatch。
- 如果 scope 存在父作用域（来自 `scopeConfig.is_subscope_of`），则尝试用父作用域的 ID 和别名完全匹配 scopeToMatch。这需要递归进行。
- 如果 scope 存在提升（来自 `scopeContext.promotions`，而这来自 `localisationPromotionConfig.supportedScopes`），则尝试用这些提升的 ID 和别名完全匹配 scopeToMatch。

作用域的合并逻辑（scope -> scopeToMerge）：
- scope 是输入的数据（从上下文中获取或推断）。
- scopeToMerge 是另一个输入的数据（从上下文中获取或推断）。
- 如果两者都为 `null`，则返回 `null`。
- 如果其中一项为 `null`，则返回另一项。
- 如果其中一项为 `any`，则返回 `any`。
- 如果其中一项为 `?`，则返回 `?`。
- 如果两者的 ID 完全匹配，则返回第一个（比较字符串，值相等，不忽略大小写）。
- 如果存在别名（来自 `scopeConfig.aliases`），则尝试用这些别名进行完全匹配，返回第一个。
- 如果存在父作用域（来自 `scopeConfig.is_subscope_of`），则尝试使用这些父作用域的 ID 和别名进行完全匹配。这需要递归进行。

额外备注：
- 作用域的匹配方式包括通配匹配（如 `any` `?`）、直接匹配（检查作用域 ID 是否值相等）、间接匹配（别名形式、继承形式等）。
- 对于间接匹配，通过直接检查 `configGroup.scopeModel` 中的属性 `base2MatchedScopes: Int2ObjectOpenHashMap<IntArraySet>`，可以减少不必要的字符串比较，优化性能。
- 目前并未更改快速文档的逻辑：规则文件中（的规则声明中）已经给出了所有必要的信息，不需要通过快速文档再次重复提示。

#### 支持内联定义 {#inline-definition}

> - 版本：v3.2.0+
> - 日期：2026.07.14+
> - 状态：TODO
> - 相关问题：https://github.com/DragonKnightOfBreeze/Paradox-Language-Support/issues/194

即通过内联脚本声明的定义，其名字可以取决于传入的参数值。

说明：
- 新增“可能声明定义”的内联脚本用法的存根索引。
- 查询内联定义时，先查询这些内联脚本用法，在对应的脚本属性上一组缓存解析信息（inlineDefinitionInfo），依赖于自身和所有内联脚本文件。
- 解析时，先找到最相关的那个内联脚本文件，对其进行展开，将定义名、定义类型等评估结果，以及内联脚本用法和定义模板的 PSI 指针，一同保存下来。
- 仅缓存 inlineDefinitionInfo，后续再转为 definitionLightElement，并且直接使用 definitionInfo 作为字段，以适配已有架构。需要进行一定的重构和调整。
- definitionLightElement 也继承自 definitionElement，但在快速文档/装订线图标等处拥有不同的行为逻辑，并且不提供内嵌提示。另外，与其他大部分 lightElement 不同，它存在一个确定的、可导航的声明处（也就是对应的内联脚本用法）。
- 在声明了定义的内联脚本用法处，提供额外的快速文档/装订线图标，以说明这一点。
- 如果定义名来自单一的脚本表达式元素，并且文本范围完全匹配，那么更完善的方案是，认为此内联定义是可重命名的。并且，可以考虑提供额外的代码高亮。

关于内联定义：
- 定义可以在脚本文件级别和脚本属性级别声明，或者以注入/内联的方式声明。
- 内联脚本不仅可能在定义声明中使用，也可以在定义声明之外（如脚本文件顶层）使用，后一种情况可用于匹配声明定义。
- 例如，在游戏目录中的部分事件脚本文件中，通过调用特定的内联脚本，并且传入参数值作为事件ID，批量声明了一组事件。
- 内联脚本在的定义声明之外使用时，插件目前不支持推断其内联脚本文件中的上下文，也不支持通过这种方法声明的定义（并加入查询器）。

#### 内联脚本文件的文件级别提示

> - 版本：v3.0.0
> - 日期：2026-07-11
> - 状态：已实施

说明：
- 如果一个脚本文件声明了内联脚本，应提供编辑器通知，而非提供代码检查。同时以文本链接的形式提供动作，以便快速查找用法。

原因：
- 代码检查仅适用于项目文件，不适用于外部库中的文件，优点是可以通过快速入口（右侧的齿轮图标）关闭或者更改高亮级别。
- 编辑器通知则没有这条限制，可以自行配置，缺点是无法通过快速入口关闭。
- 如果提供代码检查而非编辑器通知，这会导致在编写模组时，浏览游戏文件时无法得到提示，以及快速查找用法。
- 因此，需要回退，仍然提供编辑器通知，而非代码检查。
