### 分析

- [x] `icu.windea.pls.lang.resolve.CwtConfigContext` - 为了优化内存，其中的路径属性在创建上下文对象之前会进行规范化处理（`path.normalize()`）。这可能会消耗数秒钟。 (~3.9s)
  - [x] 考虑改为通过 `CwtConfigContext.create(...)` 创建上下文对象，而非直接实例化。 (<3.9s)
  - [x] `ParadoxMemberPath.path` 目前从未在生产代码中使用，考虑将路径模型（`ParadoxMemberPath` 和 `CwtConfigPath`）的 `path` 属性统一改为懒加载的属性。 (~3.6s)
- [x] `icu.windea.pls.config.option.CwtOptionMetadata` - 为了优化性能和内存，可以考虑使用更激进的数据结构。 (<1.9s)
  - 可以考虑使用相比 `UserDataHolderBase` 底层使用的 `KeyFMap` 更加激进的策略，仅在构建时可变的“用户数据映射”。
  - 通过在底层仅使用 `bitmasks: Long` 和 `elements: Array<Any>` 这两个字段，当元素个数（大于2且）不大于64时，这种策略可以获得更好的性能和内存占用。
  - [x] 作为准备，让 `CwtOptionMetadata` 实现 `MetadataMap`，让 `CwtOptionMetadataBase` 继承自 `MetadataMapBase`。这同样适用于 `CwtConfigGroupDataModel` 和 `CwtDataExpressionMetadata`。
- [x] `icu.windea.pls.core.util.KeyRegistry` - 属性 `keys` 不需要直接使用 `ConcurrentHashMap`。考虑改为不可变的集合（`List`，底层可以直接使用 `ArrayList`），仅在 `KeyProvider.register` 中注册 key 时转为可变并加锁。
- [x] `icu.windea.pls.lang.match.ParadoxExpressionMatchService.matchScriptExpression()` - 需要改为在循环之外进行取消检查 - (~5s)
- [x] `icu.windea.pls.model.expressions.ParadoxExpression` - 需要优化，缓存内部状态，尤其是 `isParameterized`。 (~1s)
- [x] `icu.windea.pls.lang.util.ParadoxExpressionManager.isParameterized()` - 可以考虑更激进的优化（单次遍历）。 (~0.6s)
- [x] （忽略）~~`icu.windea.pls.lang.resolve.ParadoxDefinitionService.resolveInfo` - 其中的 `lazyRootKeys` 可以考虑改为懒加载。目前来说，不是那么必要。 (<<1.6s)~~
- [x] （忽略）~~对于大部分 expressionMatcher 和 expressionSupport，可以考虑直接按数据类型分发，而不是每次都从头开始遍历并检查是否 `supports`。目前来说，不是那么必要。 (<1.5s)~~
