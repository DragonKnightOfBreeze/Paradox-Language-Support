# 开发规范

## 代码规范

### 命名

如何命名 EP 的实现类：

- 建议格式：`[Domain][Layer][ImplementationType][Role]`
  - `[Domain]` - 领域前缀，如 `Cwt` `Paradox` `Stellaris`
  - `[Layer]` - 分层限定，如 `Base` `Core` `Default`
  - `[ImplementationType]` - 具体的实现类型，暗示实现逻辑
  - `[Role]`  - 角色名，EP 接口名的核心部分，如 `ExpressionSupport`
  - 始终“领域优先”，确保自然分组
- 关于各种实现：
  - `Default`  - 默认实现，适用于唯一默认的场景，或者比后续实现更一般的场景
  - `Base`  - 基础实现，适用于存在内置的核心实现或扩展实现的场合
  - `Core` - 核心实现，同样内置，但是相比基础实现要更高级
- 抽象类：
  - 可以考虑把 `Base` 放到最后，如 `ParadoxScriptExpressionSupportBase`

如何命名拥有特定用途的接口：

- 可感知某一领域模型
  - `*Aware`
- 用于在语义级别解析特定领域模型（规则、表达式等）
  - `*Resolver`
- 用于提供仅适用于特定组件的工具方法（包括扩展方法）
  - `*Scope` - 限定作用域

计算（calculate） VS 评估/求值（evaluate）：

- 评估内联数学表达式（inlineMathExpression）：应当使用 evaluate，因为涉及到参数解析和上下文。
- 评估触发器（trigger）：使用 evaluate，这还需要将动态的游戏数据加入上下文。

call VS invoke：

- 核心意思完全相同，都是指“执行一段代码（如函数或方法）”。
- **call 偏向基础、直接的操作**：最常见于**静态调用**。即在编译阶段就确定了要执行哪个函数，也泛指任何普通的函数执行。
- **invoke 偏向间接、动态或特殊的执行**：常见于**反射**（通过名称调用未知方法）、**委托/回调**、**动态调用**（如 JavaScript 的 `apply`），以及**跨线程操作**（如在 UI 线程执行代码）等场景。
- 对于 scripted_trigger/scripted_effect/script_value/inline_script - 使用 call
- 对于 event - 使用 invoke（或者 trigger/fire）

### 导入

原则：

- 除少数特殊情况以外，尽可能地使用显式导入。
- 将星号导入的上限设为50。

优先使用星号导入的包名（包含子包）：

- `com.intellij.ui.dsl` - IntelliJ UI DSL
- `icu.windea.pls.lang.resolve.complexExpression.dsl` - 复杂表达式的 DSL
- `icu.windea.pls.lang.resolve.complexExpression.nodes` - 复杂表达式节点
- （待补充）

### 注释

原则：

- 文档注释默认用中文编写，除非存在特殊情况，或者需要与上下文对齐。
- 普通注释用中文或英文编写，取决于上下文。
- 以上原则主要针对 Java 和 Kotlin 代码，其他位置或者来自其他贡献者的注释没有此限制，可以任意使用中文或英文。
- 对于 Kotlin 代码中的文档注释，应偏好 Kotlin 的文档注释（KDoc）规范，而非 Java 的。

偏好：
- 如果必要，灵活地使用内联链接（如 `[PsiElement]`），嵌入到描述文本中，或者显式引用对应的代码位置。
- 如果必要，灵活地使用引用标签（如 `@see PsiElement`），显式引用对应的代码位置。
- 尽量用自然语言描述，避免引用具体的代码片段（如有必要，可以引用关键代码位置）。
- 尽量不要直接为成员属性编写文档注释，除非需要足够详细。它们应当一并放到所在的类或接口的文档注释中（使用 `@property`）。
- 尽量不要通过 `@param` 单独为方法参数编写文档注释，除非需要足够详细。它们应当尽可能地合并到对方法的描述和说明中，并在必要时通过 `[param]` 引用。

### 缓存

原则：

- 优先使用 `icu.windea.pls.core.util.CachesKt.CacheBuilder` 构建缓存。
- 优先使用 `com.github.benmanes.caffeine.cache.Interner` 去重字符串。
- `icu.windea.pls.core` 中的全局缓存，一般使用强引用的值，同时指定上限和超时。
- 规则对象这类可能数据量巨大的缓存，一般使用软引用的值。
- 与 IDE 生命周期相关的缓存，一般使用软引用的值。

### 索引

原则：

- 直接保存到文件级别的分析数据（如语言区域、文件路径等），应使用文件索引（`FileBasedIndex`）。
- 直接基于分析数据以及 PSI 的类型与结构的数据（如封装变量、本地化等），应优先使用存根索引（`StubIndex`）。
- 需要解析 PSI 引用，或者需要依赖规则数据的数据（如定义、复杂枚举等），应优先使用文件索引（`FileBasedIndex`）。
- 为了优化性能，对于文件索引，需要依赖解析得到的匹配的成员规则的数据，应考虑统一使用合并索引（`ParadoxMergedIndex`）。
- 为了优化性能，对于文件索引，应在必要时压缩写入的数据（如使用 `readOrReadFrom` 或 `readIndexedStringList`）。

### 代码结构

整体结构：

- `icu.windea.pls.core` - 通用基础设施。包括标准库、平台或第三方库的通用扩展、工具和组件。
- `icu.windea.pls.base` - 插件自身和平台集成的基础设施。包括内部状态处理、外部数据处理、环境检测、高层平台集成以及其他相关代码。
- `icu.windea.pls.cwt` - CWT 语言支持的基础设施。通常是语义无关的。
- `icu.windea.pls.script` - 脚本语言支持的基础设施。通常是语义无关的。
- `icu.windea.pls.localisation` - 本地化语言支持的基础设施。通常是语义无关的。
- `icu.windea.pls.csv` - CSV 文件语言支持的基础设施。通常是语义无关的。
- `icu.windea.pls.images` - 图片支持的基础设施。包括 SPI、编辑器、动作、元数据以及其他相关代码。
- `icu.windea.pls.config` - 规则系统的基础设施。包括规则、规则表达式、规则分组以及其他相关代码。
- `icu.windea.pls.lang` - 语义模块。包括语义匹配、语义解析、语言构造支持、语言功能支持、领域特定逻辑以及其他相关代码。
- `icu.windea.pls.integrations` - 集成模块。提供对第三方工具的集成。例如图片处理工具和检查工具。
- `icu.windea.pls.extensions` - 扩展模块。提供对第三方插件的集成和扩展。例如 JSON 和 Markdown。
- `icu.windea.pls.tools` - 工具模块。提供一些附带的实用工具和集成。例如游戏启动器和规则生成器。
- `icu.windea.pls.ep` - 用于提供语言构造支持、语言功能支持以及部分便捷功能的多种 EP 接口和实现。

关于 `icu.windea.pls.config`：

- 这里用于存放规则系统的基础设施，但并非与规则系统紧密相关的全部代码。这意味着它们通常不需要依赖游戏或模组文件。
- 诸如规则上下文、规则匹配、模板解析、模板匹配等逻辑，由于发生在语义层，相关代码通常位于 `lang.match` 和 `lang.resolve` 中。

关于 `icu.windea.pls.lang.match` 和 `icu.windea.pls.lang.resolve`：

- 这里用于存放领域特定的、语义级别的匹配和解析逻辑。
- 这里的代码相对 `icu.windea.pls.lang.util.*Manager` 中的更加底层，后者仅在必要时提取和重构到前者中，大部分仍然可以保留。
- 尽可能仅在这里（一般是在 `*Service` 中）调用涉及匹配和解析逻辑的 EP，而不是在 EP 接口的伴生对象或 `*Manager` 中。
- 为了优化编制和查询索引时的性能，有时需要直接传入 LighterAST，而非 PSI。
- 主要基于索引、引用解析和规则文件。

关于 `icu.windea.pls.config.manipulation` 和 `icu.winddea.pls.lang.manipulation`：

- 这里用于存放强调“操作”的服务，以及相关的模型类、枚举、扩展方法等。
- 这里的代码通常会转换目标（规则对象、PSI）的状态，或者直接修改为需要的状态。
- 可以发生在多个不同的阶段和级别（例如，构建解析上下文时、进行语义解析时、调用语言功能时）。
- 同时作为部分语义解析逻辑，以及部分代码重构、意向动作和快速修复的基础设施。

关于 `Service` `Manager` 和 `Util`：

- `Service` - 更加底层的服务，可以包含领域的分析、匹配或解析逻辑，这些逻辑可能需要交给具体的扩展点实现。
- `Manager` - 更加高层的管理器，可以包含各种可以直接使用的领域方法，这些方法可能需要依赖对应的服务方法。
- `Util` - 拥有特定用途的工具类，其中的方法可能仅适用于某种特定组件或功能，或者只在少数特定场合才会用到。
- `Service` 和 `Manager` 不一定必须声明为 IntelliJ 服务，如果是无状态的，它们也可以直接声明为 Kotlin 单例对象。
- 缓存逻辑一般位于 `Manager` 级别，`Service` 级别一般是直接的获取和解析逻辑，不经过缓存。

### 依赖关系

关于模块（顶级包名下的每个子包分别视为一个模块）之间的依赖关系：

- `core` 模块应尽可能避免依赖其他任何模块（尤其是 `lang` 模块），并且总是可以被其他任何模块依赖。
- `base` 模块可以在必要时依赖于其他任何模块，并且可以在必要时被其他任何模块依赖。
  - 因为其包含了各类跨模块、跨语言的基础设施代码，例如插件设置相关的代码。
  - 考虑到插件首先就是作为一个 IDEA 插件而存在的，目前不将“插件特定的基础设施”与“平台特定的基础设施”划分到不同的模块中，如同 `core` 模块的做法一样。
- `cwt` `script` `localisation` `csv` 这些语言基础设施模块应尽可能避免依赖其他任何语言基础设施模块，以及 `lang` 模块。除了使用跨语言且领域特定的接口，以及其他少数特殊情况。
  - 未来可能考虑将这些跨语言且领域特定的接口，移到 `base` 模块或者某个新增模块。
  - 即使如此，部分双向依赖仍然是难以避免，或者就是设计如此的。
- `images` 模块不应依赖于任何语言基础设施模块，以及 `configs` `lang` `tools` 模块。
- `config` 模块不应依赖于除了 `cwt` 以外的任何语言基础设施模块，以及 `images` `lang` `tools` 模块。
- `lang` 模块不应依赖于 `tools` 模块，因为后者被期望是语义无关的（尽管应当领域相关），或者仅由后者依赖前者。
- `integrations` 模块可以并且期望在必要时依赖于各个语言基础设施模块，以及 `images` `configs` `lang` 模块。
- `extensions` 模块可以并且期望在必要时依赖于各个语言基础设施模块，以及 `images` `configs` `lang` 模块。
- `tools` 模块可以在必要时依赖其他任何模块，但不应被其他任何模块依赖（除了 `base` 模块）。
- `ep` 模块应尽可能地仅被 `config` `lang` `tools` 模块依赖。它们不应被 `integrations` `extensions` 模块依赖（需要后续重构以完成达成）。

虽然期望尽可能移除模块之间的非预期的双向依赖，有时也存在导入语句仅用于文档注释的情况……

## 格式

### 文本格式

关于代码检查的描述文本（即报错文本/问题描述文本）：

- 作为标识符（名字、类型等）的英文文本应偏好使用反引号括起（而非单引号），除非在冒号之后。
- 多个标识符之间应偏好使用英文逗号隔开。

### 文档格式

整体上的原则：

- 提供中英文双语的自述文档（`README.md`）。
- 提供中英文双语的更新日志文档（`CHANGELOG.md`）。更新项的中英文双语描述的通常放到同一行。
- 提供中英文双语的参考文档（位于 `docs` 目录中）。
- 暂时仅提供英文的贡献指南文档（`CONTRIBUTING.md`）和贡献者文档（`CONTRIBUTORS.md`）。

关于更新日志文档（`CHANGELOG.md`）：

- 提供更新项的中英文双语描述，除非是可以直接引用 Issue 标题等少数情况。
- 更新项文本的标准格式是 `[tag] [topic] 描述 / Description (issue) (commit) (contributor)`，除了描述部分之外都不是必须的。
- 更新项中的标签和话题通常使用小写，多个时用 `/` 隔开，并且放到英文方括号中。
- 更新项文本中的 Issue、提交、贡献者需要使用作为链接的普通文本（而非内联代码），并且放到英文括号中。

## 测试

### 概述

原则：

- 单元测试：适用于组件/工具/扩展等的测试。通常不需要依赖 IntelliJ Platform API 或其他外部集成。
- 集成测试：适用于 PSI/索引/查询器/语义匹配/语义解析/外部集成等的测试。通常需要依赖 IntelliJ Platform API 或其他外部集成。
- 专门针对 IntelliJ Platform API 的集成测试，也被称为“平台测试”。
- 如无特殊要求，使用 Kotlin 编写单元测试和集成测试。

偏好：

- 如果一个测试类存在一个或一些确定的测试目标（而不是一个特定的主题，或者一些特定的扩展方法），应在测试类的文档注释中以 `@see TestTarget` 的形式标出。
- 如果必要，在编写测试用例时，通过 `region...endregion` 注释对其进行分组。例如同一测试类中的测试用例足够多，或者可以分为多个模块的场合。
- 如果必要，在编写测试用例时，通过额外的单行注释进行额外说明。例如，可以对测试用例的细节、边界情况、预期结果等进行说明。

技术信息：

- 工具链：Gradle + Kotlin + IntelliJ Platform API
- 测试框架：JUnit4 + IntelliJ Platform 集成测试

相关命令：

- 全量测试：`./gradlew test`（这可能需要花费数十分钟，不推荐日常使用）
- 针对特定测试类的测试：`./gradlew test --tests "fully.qualified.TestClass"`
- 针对特定关键词的测试：`./gradlew test --tests "some.keyword.**"`

### 平台测试

平台测试用于验证包括语法、语义、语言构造、语言功能在内的，依赖 IntelliJ Platform API 的方方面面的功能。

说明：
- 测试类通常继承自 `BasePlatformTestCase`。仅在少数情况下，继承自 `UsefulTestCase` 的其他子类。
- 对于简单的场合，优先考虑使用 `myFixture.configureByText(fileName, text)`。这是更加清晰、更加直观的方式。
- 对于复杂的场合，可以考虑使用 `myFixture.configureByFile(filePath)`。

### 测试数据

- 集成测试/平台测试的测试数据统一位于 `src/test/testData` 目录下。
- 默认的，根据期望的文件类型，测试数据文件应分别使用 `.cwt` `.txt` `.yml` `.csv` 扩展名。例如 `test_entries.txt`。
- 默认的，如果必要，将其中某个子目录的 `.config` 子目录作为规则目录。例如 `src/test/testData/features/index/.config`（而规则文件位于这个目录的 `core` 子目录中）。
- 为了明确表明这是一个测试数据文件，可以在文件名中包含 `.test`。例如 `example.test.txt`。
- 为了显式指定游戏类型，可以在文件名中包含 `.{gameTypeId}`。例如 `example.stellaris.txt`。
- 对于脚本文件、本地化文件和 CSV 文件，需要在 `doSetUp()` 中调用 `markIntegrationTest()`，以从文件名推断文件类型和游戏类型。

### 测试作用域

对于平台测试，`ChronicleTestScope` 中提供了一组实用的作用域方法。
其中包括一些相对通用的方法，以及另外一些领域特定的方法（用于注入上下文信息、处理规则数据等）。

对 `ChronicleTestScope` 中的部分关键作用域方法的说明：
- `markIntegrationTest()` - 启用仅用于平台测试的特殊行为。这会启用从文件名推断文件类型和游戏类型。
- `clearIntegrationTest()` - 关闭仅用于平台测试的特殊行为。这会一并清空注入状态。
- `markRootDirectory(relPath)` - 注入游戏或模组的根目录。传入的路径相对于测试数据目录（`src/test/testData`）。用于测试的游戏或模组文件通常不需要实际位于这个目录（或其子目录）中。
- `markConfigDirectory(relPath)` - 注入规则目录。传入的路径相对于测试数据目录（`src/test/testData`）。规则文件应位于这个目录的特定子目录中（而不是直接位于这个目录中）。例如通用的规则文件应位于 `core` 子目录中，Stellaris 的规则文件应位于 `stellaris` 子目录中。参见 `ParadoxGameType`。
- `createRootInfo(gameType, gameVersion)` - 创建注入的根信息。可用于额外指定游戏版本。
- `markFileInfo(gameType, path, ...)` - （为后续配置的测试数据文件）注入文件信息。传入的路径相对于入口目录（其不一定同时是游戏或模组目录）。例如应直接传入 `events/test_events.txt`，而非传入 `game/events/test_events.txt`。参见 `ParadoxGameTypeMetadata`。
- `VirtualFile.injectFileInfo(gameType, path, ...)` - （为当前的测试数据文件）注入文件信息。类似前者。
- `initConfigGroups(project, ...gameTypes)` - 为指定的一组游戏类型初始化规则分组。使用注入的和内置的规则文件。通用的规则分组（`core`）总是会被初始化。

对于需要注入上下文信息（如文件信息）或需要基于规则数据的平台测试：
- 需要在 `doSetUp()` 中按需调用 `markRootDirectory()` `markConfigDirectory()` 和 `initConfigGroups()`，并在测试方法中按需调用 `markFileInfo()` 和 `injectFileInfo()`，以正确地注入需要的上下文信息。
- 如果测试失败，需要考虑到这可能是由于未指定根目录（某些缓存位于根目录级别）、未正确注入规则文件、未加载规则分组等原因导致的。
- 注入的文件路径（通过 `markFileInfo()` 或 `injectFileInfo()`）不需要与实际的文件路径对齐。例如，它们可以拥有不同的文件名，实际的文件也可以直接来自 `myFixture.configureByText(fileName, text)`。
- 使用的测试数据文件（就真实游戏来说）不需要是实际可用的。例如，可以组合使用完全自定义的规则文件和脚本文件，只要符合格式和规范。

参见：
- `icu.windea.pls.test.ChronicleTestScope`
- `icu.windea.pls.test.chronicle.ChronicleHelloWorldTest`

### 测试 DSL

对于单元测试和平台测试，`icu.windea.pls.test.dsl` 中提供了一些实用的 DSL，以及对应的作用域方法。

关于 `ExpectDsl`：
- 可以在 `expectScope {...}` 中，以扩展函数的格式进行断言。
- 这些方法直接返回其接收者，并在必要时适用 kotlin Contract 以及更改返回类型。
- 断言消息 `message` 通常作为最后一个可选的参数。

关于 `HighlightingDsl`：
- 可以在 `highlightingScope {...}` 中，以字符串插值的格式构建用于检查代码高亮结果的测试数据文本。
- 这种方式相比直接使用原始文本或原始文件，更加可读和可维护。
- 另外也提供了 `myFixture.configureByText(fileName) {...}` 和 `myFixture.createFile(fileName) {...}`。

示例：
- `expectScope { result.expectNotNull().someMethodForNonNullType() }`
- `expectScope { result.expectIs<SomeType>().someMethodForThisType() }`
- `myFixture.configureByText("test.txt") { "${error(message)}key${errorEnd} = value" }`

参见：
- `icu.windea.pls.test.dsl.ExpectDsl.kt`
- `icu.windea.pls.test.dsl.HighlightingDsl.kt`
- `icu.windea.pls.test.chronicle.ChronicleHelloWorldDslTest`

### 解析测试

解析测试（ParsingTestCase）用于验证各个自定义语言的词法分析和语法分析是否正确。各个测试数据文件都有一份对应的 PSI 树快照文件。

示例：
- `icu.windea.pls.script.ParadoxScriptParsingTest`

### 高亮测试

有些平台测试需要验证测试数据文件是否具有正确高亮，这些测试被称为“高亮测试”。例如针对注解器（annotators）和代码检查（codeInspections）的测试。

说明：
- 对于简单的场合，优先考虑通过 `myFixture.configureByText(fileName, text)`，并在测试数据文本中结合使用需要的作用域方法，来编写测试用例。
- 对于复杂的场合，可以考虑直接在对应的测试数据文本或测试数据文件中指定高亮信息（如 `<warning descr="...">target</warning>`），来编写测试用例。

示例：
- `icu.windea.pls.script.annotator.ParadoxScriptSyntaxAnnotatorTest`
- `icu.windea.pls.lang.inspections.script.common.IncorrectSyntaxInspectionTest`

### 受限测试

部分测试是不会默认执行的。除了通过 `@Ignore` 直接忽略以外，更常见的方式是通过系统属性（system properties）显式启用。

例如，`ParadoxModImporterTest` 依赖于本地化环境，因此仅在 `chronicle.test.include.all=true` 或 `chronicle.test.include.local.env=true` 时才会启用。

参见：
- `icu.windea.pls.test.ChronicleAssume`
- `icu.windea.pls.test.ChronicleTestCapacities`
