# 领域：规则系统 覆盖规则

> 目标：梳理 PLS「覆盖规则」（`overrides` / 原「优先级规则」）的语义、来源与数据获取方式，并记录各游戏覆盖策略的确定程度与依据。
>
> - 版本：3.0.4-dev
> - 日期：2026-10-02
> - 状态：探索性笔记（`ai-notes` 按原样存档；后续项目状态可能变化）

## 1. 背景与定位

覆盖规则用于指定**目标目录（相对于入口目录）**的覆盖策略，影响目标的**生效顺序**与**查询结果排序**（流式查询除外），并被用于覆盖相关的代码检查。

- 数据模型：`icu.windea.pls.config.model.CwtConfigGroupDataModel.overrides: Map<String, CwtOverrideConfig>`
- 配置对象：`icu.windea.pls.config.config.detached.CwtOverrideConfig`（`filePath` + `strategy`）
- 策略枚举：`icu.windea.pls.model.overrides.ParadoxOverrideStrategy`
- 解析入口：`icu.windea.pls.ep.config.configGroup.CwtConfigGroupProcessors.FileBased`（读取 `overrides = { ... }`）
- 策略提供者：`icu.windea.pls.ep.overrides.ParadoxBaseOverrideStrategyProvider`（经 `ParadoxFilePathMapBasedOverrideStrategyProvider` 匹配路径）
- 规则文件：
  - 通用：`cwt/core/00_overrides.cwt`
  - Stellaris：`cwt/cwtools-stellaris-config/config/overrides.cwt`
  - EU5：`cwt/cwtools-eu5-config/config/overrides.cwt`
  - VIC3：`cwt/cwtools-vic3-config/config/overrides.cwt`
- 文档：`docs/zh/ref-config-format.md#config-override`、`docs/en/ref-config-format.md#config-override`

### 四种覆盖策略

| 策略 | 含义 | 近似引擎行为 |
| --- | --- | --- |
| `fios` | First In, Only Served | 只读一次；先加载者生效，后者被忽略 |
| `lios` | Last In, Only Served | 后读覆盖（默认） |
| `dupl` | Duplicates | 整文件覆盖；必须用同路径文件整体替换 |
| `ordered` | Ordered | 顺序读取；按序新增或合并，不覆盖既有条目 |

> 注意：插件的策略是**查询/检查语义的近似**，并非引擎内部数据结构的精确复刻。例如 `common/relics`=「不可覆盖」，只能以 `fios` 近似。

## 2. 核心问题：如何确定覆盖策略

引擎行为没有公开的权威规范，因此只能从**可信或可参考的来源**推断：

1. **IronyModManager (IMM)** —— 最「确定性」的来源（见 §3）。
2. **Stellaris 英文百科「文件覆盖列表」** —— 人工维护、逐目录列举（见 §4）。
3. **CWTools / 本仓库既有规则文件** —— 历史沉淀的整理值（可能已过时）。
4. **官方 wiki / 社区教程** —— 佐证（直接抓取可能被 Cloudflare 拦截，见 §4）。
5. **README 列出的其他参考工具** —— 如 `amtep/tiger`（检查模组文件常见错误）、`nickbabcock/jomini`（解析 Paradox 文件）等，可能间接编码了加载/覆盖行为，值得后续挖掘。

原则：**多来源交叉验证 + 标注可信度**，冲突处逐条注明，而不是强行统一。

## 3. IMM：确定性的数据结构

IMM（<https://github.com/bcssov/IronyModManager>）为 Stellaris 提供了两处可直接解析的数据：

### 3.1 FIOS 路径列表

`src/IronyModManager.IO/Mods/InfoProviders/StellarisDefinitionInfoProvider.cs` 的 `FIOSPaths` 列出「只读一次」目录：

`component_sets`、`component_templates`、`event_chains`、`global_ship_designs`、`scripted_variables`、
`section_templates`、`ship_behaviors`、`special_projects`、`strategic_resources`、`events`、
`solar_system_initializers`、`traits`、`start_screen_messages`、`governments/authorities`。

其匹配方式为 `ParentDirectory.EndsWith(path)`；输出文件名以 `!!!_` 前缀 + 升序编号（先加载者胜出）。

### 3.2 解析器映射

`References/CopyAll/Maps/StellarisParserMap.json` 将目录映射到解析器。可据此推断：

| IMM 解析器 | 推断策略 | 说明 |
| --- | --- | --- |
| 命中 `FIOSPaths` | `fios` | 先加载者胜出 |
| `*WholeTextParser` | `dupl` | 整文件作为整体处理 |
| `StellarisOverwrittenObjectSingleFileParser` | `dupl` | 整体替换的「单文件对象」 |
| `*OverwrittenParser` | `lios` | 键级对象替换 |
| `*KeyParser` / `DefaultParser` / `*DefinesParser` | `lios` | 默认后读覆盖 |
| `GenericLocalizationParser` | `lios` | 本地化；惯例是放入 `replace/` 目录（`zzz_` 前缀） |

> 局限：`WholeText` 往往是 IMM「无法解析」时的兜底，不能直接等同于引擎的整文件覆盖。
> 例如 `common/on_actions` 在 IMM 中被列为 `GenericWholeTextParser`，但引擎实际是**自动合并**。

### 3.3 复现脚本

`scripts/util/fetch_override_strategies.py` 会：

- 将 IMM 解析到**固定 commit**（默认 `master`，脚本内记录 SHA）；
- 解析 `FIOSPaths` 与 `StellarisParserMap.json`；
- 按上表推断每个目录的策略；
- 与现有 `overrides.cwt` 做差异对比。

```powershell
python scripts/util/fetch_override_strategies.py --out build/overrides.md
```

本次运行基准：IMM `master` @ `6a8861d734382a9e98f7394ea404fac7a2b884b3`（2026-10-02）。

## 4. Stellaris 百科覆盖列表

Stellaris 英文百科有一份「各文件覆盖规则列表」，并按目录给出规则（后读覆盖 / 只读一次 / 整文件覆盖 / 不可局部覆盖 / 自动整合等）。

- 中文译文（Stellaris Mod Group / pdxdoc，可作为可访问镜像）：<https://main--pdxdoc-next.netlify.app/guides/other/overwrite/>
- 该页明确说明其列表**翻译自英文百科，并不一定准确，仅供参考**。
- 直接抓取 `stellaris.paradoxwikis.com` 等站点会返回 Cloudflare 挑战页（约 3KB），无法稳定自动化；因此以 pdxdoc 译文作为访问代理，并在规则文件中标注为次级来源。

## 5. Stellaris 结论与冲突

综合 IMM 与百科列表，与既有配置的差异如下（详见脚本生成的差异报告）：

| 目录 | 既有 | IMM | 百科 | 处理 |
| --- | --- | --- | --- | --- |
| `common/star_classes` | `fios` | `lios` | 只读一次 | 保留 `fios`（[高]，IMM 属局限） |
| `common/static_modifiers` | `fios` | `lios` | 只读一次 | 保留 `fios`（[高]） |
| `common/scripted_loc` | `fios` | `lios` | 未明确 | 保留 `fios`（[中]，存疑） |
| `common/relics` | `fios` | `lios` | 不可覆盖 | 保留 `fios` 近似（[低]） |
| `common/technology` | `dupl` | `lios` | 必须整文件覆盖 | 保留 `dupl`（[中]） |
| `common/traits` | `dupl` | `fios` | 不可局部覆盖 | 保留 `dupl`（[中]） |
| `common/diplomatic_actions` | `dupl` | `lios` | 必须整文件覆盖 | 保留 `dupl`（[中]） |
| `common/governments/authorities` | `dupl` | `fios` | 必须整文件覆盖 | 保留 `dupl`（[中]） |
| `common/ethics` | `lios` | `dupl` | 后读覆盖但建议整文件 | 保留 `lios # lenient dupl`（[中]） |
| `common/observation_station_missions` | `dupl` | `lios` | 未明确 | 改为 `lios`（[低]；旧注释依据已失效） |
| `common/strategic_resources` | `fios` | `fios` | 只读一次 | 保留；更新注释（IMM 已与旧注释不一致） |

补充发现（当前未加入配置，因默认即 `lios` 或影响甚微）：

- `common/species_rights/*`（9 个子目录）：IMM 为 `OverwrittenObject`（`lios`）。
- `prescripted_countries`：IMM 为 `OverwrittenObject`（`lios`）。
- `common/inline_scripts/**`：IMM 作为整文件处理（属其局限）；内联脚本实际按定义键处理，倾向 `lios`，待确认。
- `common/governments/authorities` 内的 `advanced_authority_swap`：IMM 标记为 `FlatMerge`，属于对象级合并，不对应目录级覆盖策略。

## 6. 各游戏现状

| 游戏类型 | 规则文件 | 数据来源与可信度 |
| --- | --- | --- |
| 通用 | `cwt/core/00_overrides.cwt` | 多来源综合；主要依据 Stellaris 验证，其他游戏待确认 |
| Stellaris | `.../overrides.cwt` | IMM（确定性）+ 百科列表；最高（含逐条可信度标注） |
| EU5 | `.../overrides.cwt` | 项目惯例；尚未核对来源（[低]） |
| VIC3 | `.../overrides.cwt` | 项目惯例；尚未核对来源（[低]） |
| CK2 / CK3 / EU4 / HOI4 / IR / VIC2 | （无） | 未定义游戏级覆盖；沿用通用规则与内置的强制策略（如 `ParadoxForcedDefinitionOverrideStrategyProvider`） |

> IMM 只完整实现了 Stellaris（`IsFullyImplemented == true`）；HOI4 的 provider 为未实现（`FIOSPaths` 抛异常）。因此其他游戏需要各自寻找来源。

## 7. 扩展到其他游戏的方法

1. 优先查找该游戏对应的 **IMM 解析器映射**（`References/CopyAll/Maps/<Game>ParserMap.json`）与 provider（若有）。
2. 查找该游戏 **官方 wiki 的覆盖/加载顺序页面**；若被拦截，寻找可信镜像/翻译/社区文档。
3. 查阅该游戏 **CWTools 配置仓库**与本仓库历史配置，作为基线。
4. 用 `scripts/util/fetch_override_strategies.py` 的相同思路编写脚本，固定 commit，生成候选表并与现有配置做差异对比。
5. 交叉验证后，在对应 `overrides.cwt` 中逐条标注**来源、可信度、冲突**；更新本笔记。
