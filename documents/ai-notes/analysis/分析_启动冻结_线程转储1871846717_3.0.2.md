# 分析：IDE 启动冻结（P18，线程转储 1871846717）

> 版本：v3.0.2
> 日期：2026-09-02
> 相关：`documents/notes/问题追踪.md` 中的 P18、P3、P17
> 素材：`documents/notes/assets/thread-dump-1871846717.txt`

基于线程转储（约 1.2 MB，6329 行）与 P18 中记录的 async-profiler 墙钟采样数据，分析 IDE 在 IDEA 2025.2（通过 `runIde`）上启动时明显卡顿（冻结数分钟）的根本原因。

## 一、问题背景

- 现象：IDEA 2025.2 上通过 `runIde` 启动插件，IDE 启动阶段明显卡顿/冻结。
- 对照：IDEA 2026.2.1 上不存在此问题（至少数秒内就能一切就绪）。
- P18 中的 profiling 数据（总时间，墙钟采样）：

```
icu.windea.pls.config.config.CwtFileConfigResolver.resolve(VirtualFile, CwtConfigGroup, String) - 317.88s
icu.windea.pls.cwt.CwtParserDefinition.createElement(ASTNode) - 267.685s
icu.windea.pls.ep.config.configGroup.CwtFileBasedConfigGroupProcessor.process(CwtConfigGroup, Continuation) - 71.264s

CwtElementTypes$Factory.createElement - 267.6s (cpu time: <<51ms, total time: 267.6s)
```

关键疑点：`createElement` 总时间 267.6s、CPU 时间仅约 51ms——总时间与 CPU 时间相差约 5000 倍，说明这些帧在栈上时线程几乎一直处于等待状态，而非在计算。

## 二、分析过程

### 2.1 线程转储概览

转储由 `CoroutinesKt$backgroundWriteAction$2$dumpJob$1`（coroutines.kt:317）触发——即平台对**长时间运行的后台写动作**的看门狗主动 dump，说明转储时刻存在一个超时的后台写动作。

统计全部线程（约 90 个）后，无任何 `BLOCKED` 状态的线程、无死锁，只有少量 `RUNNABLE` 线程与大量 `WAITING`/`TIMED_WAITING` 线程。这排除了死锁与 CPU 忙循环。

### 2.2 正在运行的后台写动作

`DefaultDispatcher-worker-15 @JpsGlobalModelSynchronizerImpl#3277`（带 `RunInBackgroundWriteActionMarker`）正在执行：

```
backgroundWriteAction (CoroutinesKt.kt:314)
 > JpsGlobalModelSynchronizerImpl.delayLoadGlobalWorkspaceModel (JpsGlobalModelSynchronizerImpl.kt:195)
 > GlobalWorkspaceModel.updateModel (GlobalWorkspaceModel.kt:154)
 > WorkspaceModelImpl.updateProjectModel (WorkspaceModelImpl.kt:203)
 > fireBeforeRootsChanged / beforeChanged
 > MessageBus 懒加载各插件的监听器类
 > PluginClassLoader.loadClassInsideSelf -> defineClass2 (另见 worker-22 的栈)
```

写动作内部的 `beforeRootsChange` 事件通过 MessageBus 发布时，会懒订阅各插件的监听器，触发大量插件类加载（`doLoadClass` → `UrlClassLoader.consumeClassData` → `defineClass2`）。在 `runIde` 的调试 JVM（转储中可见 JDWP 相关线程）下，类加载被进一步拖慢。

### 2.3 所有读动作消费者均被卡在等待读许可

- 插件配置分组初始化协程 `ChronicleFacade$CoroutineScopeService#896/#899/#907/#916/#921` 等，全部 `SUSPENDED` 于 `InternalReadAction.readLoop(InternalReadAction.kt:71)`，调用链为：

```
CwtConfigGroupService.processConfigGroups (CwtConfigGroupService.kt:79)
 > CwtConfigGroupBase.init -> doInit -> doApplyProcessors
 > CwtFileBasedConfigGroupProcessor.process (CwtConfigGroupProcessors.FileBased.kt:115)
 > readAction { resolveFileConfig(...) }  // 逐文件发起挂起式读动作
```

- VFS 刷新线程（`DefaultDispatcher-worker-23/33` 等）同样卡在 `smartAcquireReadPermit`/`acquireReadPermit` → `RunSuspend.await`（`RefreshWorker.partialDirRefresh`）。
- 任务指示器存在 `Indexing paused` 状态；索引 chunk 正在 attach（`ApplicationImpl pooled thread 8` 的 `attachChunksFromPreviousIDESession`）。
- AWT 线程处于 `ApplicationImpl.postInit` → `SuvorovProgress.dispatchEventsUntilComputationCompletes` → `EternalEventStealer.dispatchAllEventsForTimeout`，且其事件分发走 `runPreventiveWriteIntentReadAction` → `acquireWriteIntentPermit` → `RunSuspend.await`——EDT 的"预防性写意图"也在排队。

### 2.4 与 profiling 数据的印证

P18 的墙钟采样显示插件规则解析路径总时间约 317s，其中 `CwtElementTypes$Factory.createElement` 267.6s（CPU 仅 ~51ms）。这与转储中"插件读动作长期挂起等待"完全吻合：

- 读动作的执行体（`resolveFileConfig` → PSI 创建等）只在实际获得读许可、真正在栈上执行时才会被采样；
- 总时间/CPU 时间比高达数千倍，说明执行体被反复中断/等待——正是"读动作排队等许可"在墙钟采样下的形态；
- 317s 的量级与"启动冻结数分钟"的现象一致。

### 2.5 形成机理

IDEA 2025.2 引入了新的 `NestedLocksThreadingSupport` 读写许可调度（配套 `RunSuspend`、`EternalEventStealer`、`SuvorovProgress`），其调度对写动作偏好更强：一旦存在 pending 的写意图，新的读动作即排队；且 EDT 本身会挂一个预防性写意图，进一步压制读动作。启动阶段平台连续产生写动作（JPS 模型延迟加载 → roots change → VFS 刷新 → 索引写入），其间插件初始化所依赖的读动作流被长期饿死，形成锁护送（convoy）效应：

```
启动写动作（JPS sync / roots change / 索引写入）
  ├─ 插件配置分组初始化：数千个逐文件挂起式 readAction ──┐
  ├─ VFS RefreshWorker 读动作 ──────────────────────────┤ 全部排队等读许可
  └─ AWT postInit 启动进度（等待上述完成）──────────────┘ → 整体冻结
```

插件在其中的放大作用：

- `CwtConfigGroupService.initConfigGroupsAsync` 在项目打开时非取消地初始化**所有** game type 的分组（项目级 + 应用级），见 `processConfigGroups` 中对 `ChronicleFacade.getConfigGroup(configGroup.gameType)` 的补充初始化；
- `forEachConcurrent` 对分组并行处理，而 `CwtFileBasedConfigGroupProcessor` 对**每个 CWT 规则文件**单独发起一个挂起式 `readAction`（resolve/process 共约 4 轮），数千个读动作在 2025.2 的新锁实现下逐个排队，每个都承受一次调度延迟。

## 三、结论

1. **根本原因**：IDEA 2025.2 的 `NestedLocksThreadingSupport` 在启动阶段（长后台写动作 + 连续写意图）对大量挂起式读动作造成严重饥饿。这不是死锁、不是 CPU 热点，而是纯粹的锁调度问题。
2. **直接表现**：插件在项目打开时的规则分组初始化是启动关键路径上最大的一批读动作消费者，被饿死约 5 分钟（profiling 中 317s），而该初始化是 AWT `postInit` 启动进度所等待的组成部分，因此 IDE 表现为冻结。
3. **版本差异**：相同代码在 IDEA 2026.2.1 上数秒内就绪，说明平台在新版本中改进了读写许可的调度公平性/交错策略，读动作不再被饿死。因此这是一个 **IDEA 2025.2 平台级兼容性问题**，并非插件自身存在死锁或逻辑错误。

## 五、后续建议（仅记录，未做任何更改）

- 若需要兼容 2025.2，可考虑防御性优化：把逐文件 `readAction` 合并为分组/批量读动作；项目打开时懒初始化非 core 游戏分组；限制 `forEachConcurrent` 的并发度。
- 验证手段：在 2025.2 上用 async-profiler wall 模式复现，确认 `RunSuspend.await`/`InternalReadAction.readLoop` 的等待占比。
- 若不考虑 2025.2 的兼容性，可参照 P17 的处理方式，将其标记为 IDE 版本兼容性问题而忽略。
